# Proposal

## Why

The redesigned campaign page shows who plays each character ("de Marina") and, to players, who runs the campaign ("mestrada por Ana"). The core knows no one's name but the requester's, and must not copy names from Keycloak: identity data belongs to the identity provider, and silently copying it is neither up to date nor a good fit for LGPD.

What the page needs is not a person's legal name but how they want to be called **at that table**. That is product data the user gives for one purpose, so the core can keep it, scoped to the campaign it was given for.

## What Changes

- **Table names**: every campaign member has a name used only inside that campaign.
  - The DM gives theirs (`dm_name`) when creating the campaign; it is stored on the campaign.
  - A player gives theirs (`player_name`) when accepting an invite, with their own character or a premade one; it is stored on that character while it is in the campaign.
  - Both are required at those moments, trimmed, 1 to 50 characters.
- **Campaign details gain names**: `dm_name`, and `player_name` on each item of `characters`. Only campaign members see them, as today.
- **Names live and die with the table**: leaving or being removed from a campaign, or deleting the campaign, clears the player's table name; deleting the campaign or the character deletes the names with it.
- **Editing**: the DM changes `dm_name` through `PATCH /campaign/{id}`; a player changes their `player_name` through `PATCH /character/{id}`, only while the character is in a campaign. Nobody edits someone else's table name.
- The frontend suggests the user's first name from their own session as the default; the core never reads names from Keycloak.

Out of scope: a global profile or nickname, suggesting the last table name used, names in lists or invites.

## Capabilities

### New Capabilities

- `table-names`: How campaign members name themselves at a table, and when those names are set, changed and removed.

### Modified Capabilities

- `campaign-details`: Includes the DM's and each player's table name.
- `character-edit`: The edit request may change the player's table name instead of, or together with, the character name.

## Impact

- **Database**: `campaign.dm_name` (required) and `character_sheet.player_name` (set while in a campaign) are added to `0001_init`: the database is recreated from scratch one last time for this change. Later schema changes get their own migration.
- **API**: `dm_name` required on `POST /campaign`; `player_name` required on `POST /invite/{hash}/accept`; new `PATCH /campaign/{id}` (DM only, `dm_name`); `PATCH /character/{id}` accepts `player_name`; `dm_name` and `characters[].player_name` on `GET /campaign/{id}`. **BREAKING** for clients creating campaigns or accepting invites without the new fields.
- **Code**: campaign and character domain (table name value object, policies), create campaign, accept invite, leave campaign, campaign deletion and edit use cases, repositories, read models, responses, Swagger annotations (regenerated by CI).
- **Frontend**: the create campaign and accept invite forms ask for the table name, prefilled with the session's first name; the campaign page shows the names (`campaign-detail-redesign`).

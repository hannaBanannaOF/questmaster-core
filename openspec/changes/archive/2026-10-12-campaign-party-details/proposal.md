# Proposal

## Why

The frontend campaign page should show the party as character cards: linked to each sheet, with current and max HP, and the requester's own characters marked. The campaign details only return `id`, `name` and `current_hp` per character, so the frontend cannot link to a sheet (it needs the slug) or show "3 / 10 HP".

While checking whether members may open each other's sheets, we found that `GET /core/api/v1/character/{characterID}` has no access check: any authenticated user can read any character by id, including characters of campaigns they are not part of.

## What Changes

- Each character in the campaign details gains `slug`, `max_hp` and `is_mine` (true when the requester is the character's player).
- **BREAKING**: character details are visible only to the character's player, the DM of the character's campaign, and players with a character in the same campaign. Anyone else receives 403. A character without a campaign is visible only to its player.

Out of scope: the player's name on each character (the core does not store users), and letting the DM edit HP from the campaign page (the DM may already update HP through the existing endpoint; the frontend change is separate).

## Capabilities

### New Capabilities
- `character-details`: Who can read a character's details.

### Modified Capabilities
- `campaign-details`: Adds the character fields returned with the campaign details.

## Impact

- **API**: Additive fields in the campaign details. `GET /character/{characterID}` returns 403 for non-members, where it returned 200 before.
- **Code**: campaign details read model and mapper (characters already loaded with `cs.*`), character details use case (load the campaign membership before returning), character policy and errors, Swagger annotations (regenerated by CI).
- **Frontend**: the campaign page renders party cards linked to each sheet; a non-member opening a sheet sees the existing "not found" page.
